# P3-1 — E-core 后台分流 (QoS Class 注入 ThreadPool)

**Date**: 2026-05-15
**Branch**: `feat/260515-ecore-qos`
**Doctrine**: §6 P3 第 1 条 + §7.2 第 3 条 (基准用 P-core 强制)
**Hardware**: Apple M5, macOS 26.5 (Tahoe). 4 P-core + 6 E-core, 总 10 logical CPU
**Microbench**: `bench/microbench/ecore_qos_gate.cpp` (commit `34ea549`)

---

## 1. Motivation

doctrine §6 P3 第 1 条 "E-core 后台分流(QoS Class 注入 ThreadPool)" 与 §7.2 第 3 条 "基准用 P-core 强制 `pthread_set_qos_class_self_np(QOS_CLASS_USER_INITIATED, 0)`" 是配对项. 全项目 `grep qos_class` 0 命中 — ThreadPool 从未调用 QoS API, 6 个 worker (10 default - 4 P-core) 可能漂移到 E-core, 基准失真风险确实存在.

## 2. 实施 (Stage B+C)

### B. ThreadPool worker QoS 注入 (commit `849e453`)

- `include/gnfs/util/thread_pool.hpp`:
  - 加 `#include <pthread.h>` + `<sys/qos.h>` (macOS only)
  - `enum class QoSClass`: `UserInitiated` / `Utility` / `Background` / `Unspecified`
  - `inline set_current_thread_qos()` static helper — main thread 也用
  - `ThreadPool` ctor 加 `qos` 参数 (默认 `UserInitiated`)
  - `worker_loop` 入口 call `set_current_thread_qos(qos_)`
  - Linux: 编译为 no-op

### C. Main / bench entry QoS (commit `0f12535`)

- `src/cli/main.cpp` 入口 set `UserInitiated`
- `bench/microbench/spmv_neon_gate.cpp` 入口 set `UserInitiated`
- `bench/microbench/bw_block_only_loop.cpp` 入口 set `UserInitiated`

## 3. Microbench 设计 (Stage D)

`ecore_qos_gate.cpp` 跑 4 个 `(worker_count × QoS class)` 组合的 scalar 64-bit forward SpMV:

| Trial | Workers | QoS class | 含义 |
|---|---:|---|---|
| 1 | 4 | UserInitiated | 4 P-core only baseline |
| 2 | 10 | UserInitiated | 4P + 6E hint USER (**default after Stage B**) |
| 3 | 10 | Unspecified | system default scheduling |
| 4 | 10 | Background | hint E-core forced (上限对照) |

Matrix: 278K × 10K, nnz 9.77M (BW path 典型规模). 每 trial: 3 warmup + 3 trials × 30 reps, 取 median.

## 4. Results

| Trial | Worker | QoS | Wall (ms/rep) | Notes |
|---|---:|---|---:|---|
| 1 | 4 | USER | 1.17 - 1.51 | P-core only |
| 2 | 10 | USER | **0.87** | **default after Stage B** |
| 3 | 10 | DEF | 0.86 | system default |
| 4 | 10 | BG | **4.51 - 4.78** | hint E-core forced |

### Speedup factors

| Comparison | Factor | Interpretation |
|---|---:|---|
| 10-USER / 4-USER | 1.33-1.74× | 加 6 个 E worker 的边际收益 (E-core 共贡献 ~40-58% 加速) |
| **10-BG / 10-USER** | **5.18 - 5.44×** | **P-core hint 的绝对收益.** 若 worker 漂移 E-core, 基准失真 5× |
| 10-DEF / 10-USER | 0.99-1.00× | macOS 已隐式给前台 CLI USER QoS, default ≈ USER hint |

## 5. Key findings

### 5.1 P-core hint 极限收益 5.18×

**最关键数据**: `10-BG / 10-USER = 5.18×`. 假设 worker 全部漂移到 E-core, BW SpMV wall 会被夸大 5×. doctrine §7.2 第 3 条 "基准用 P-core 强制" 的数据基础得到验证.

实际生产中很少出现 10 worker 全 E-core, 但 partial 漂移 (例如 4 个落 E-core) 仍可造成 ~20-30% 失真. **显式 set USER QoS 把这个风险消除到 0**.

### 5.2 macOS default ≈ USER (10-DEF ≈ 10-USER)

意外发现: 在当前 GNFS CLI 默认运行下, system default scheduling 实测 wall ≈ USER hint (0.86 vs 0.87 ms). 推测原因:
- macOS 给前台 CLI 进程的 main thread 默认 `QOS_CLASS_USER_INTERACTIVE`
- worker thread 继承 main thread QoS → 隐式接近 USER

这意味着在当前 GNFS 主路径下, Stage B+C 改动**实测 wall delta ≈ 0**. 但显式 set QoS 仍有价值:

1. **跨平台显式化** — Linux no-op, macOS 显式 USER. 不依赖 macOS scheduler 隐式行为
2. **防退化** — 如果未来 GNFS 改成 `nohup` / launchd 守护 (常驻后台), main thread QoS 会降到 `UTILITY`, worker thread 继承后**实测会落入 10-BG 区域** (5× 性能损失). 显式 set USER 覆盖这个 regression
3. **doctrine §7.2 第 3 条 落地证据** — code 里有显式 `pthread_set_qos_class_self_np` 调用, 不再需要 wrapper script
4. **Background opt-in** — 加了 `QoSClass::Background` 选项后, 真有后台任务时可显式 `ThreadPool pool(N, QoSClass::Background)` 让出 P-core

### 5.3 加 6 E worker 仍有 1.33-1.74× 边际收益

`10-USER / 4-USER = 1.33-1.74×`. 即使 6 个 worker hint USER 但实际仍可能落 E-core (P-core 已饱和), E-core 仍贡献约 ~33-74% 加速. **这就是为何 GNFS 默认 10 worker 而非 4 worker**:
- E-core 性能 ~1/2 P-core, 但 6 个 E-core ≈ 3 P-core 等效, 加上 4 P-core = ~7 P-core 等效
- 4 P-core baseline 1.51 ms, 7 P-core 等效 ≈ 1.51/1.75 ≈ 0.86 ms ✓

模型与实测一致.

## 6. 决策与未来工作

### 关闭

- **doctrine §6 P3 第 1 条**: QoS Class 注入 ThreadPool ✅
- **doctrine §7.2 第 3 条**: 基准用 P-core 强制 ✅ (作为 code-level pthread_set 而非 wrapper script)

### 未来工作 (BACKLOG)

1. **后台 GNFS daemon QoS validation** — 当未来添加 `nohup` / launchd 模式时, 实测 wall 应**仍 ≈ 10-USER** (因显式 set USER). 验证防退化机制有效
2. **Linux QoS 等价** — Linux `sched_setattr` + cgroups 可达到类似效果, 但当前 ThreadPool no-op fallback 已经足够 (Linux scheduler 默认即可). 触发: Linux CI runner 出现 P-core/E-core 异构 (如 AWS Graviton 3E)
3. **Hybrid worker pool** — 给 ThreadPool 加 `(p_workers, e_workers)` 参数, 前者 USER 后者 BG. 触发: 真实生产 workload 有混合 throughput-vs-latency 需求 (目前 GNFS 是纯 throughput)

## 7. 教训

1. **doctrine 铁律 5 (measurement-first) 又一次救场**. 看到 `grep qos 0 命中` 就匆忙得出"必须改" 的判断会过激. 实测 10-DEF ≈ 10-USER 表明 macOS 默认行为已经 OK — 这个改动是**预防性 + 显式化**, 而非紧急 fix
2. **极限对照(10-BG) 的价值**: 直接对比 10-USER vs 10-DEF 只看到 1% 差异, 容易认为 "QoS 不重要". 加 10-BG 才暴露真实 5× 极限 — 当外部条件改变 (后台 daemon mode) 时, 这个 5× 会爆发. 极限边界测试比正常情况测试更有信号
3. **跨平台 #ifdef 模式**: `QoSClass enum` + `set_current_thread_qos` 抽象让 Linux 编译为 no-op 而不需要 #ifdef 满天飞. ThreadPool ctor 接口跨平台一致, 仅实现内 #ifdef. 是好的设计
